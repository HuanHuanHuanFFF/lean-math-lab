## 5. 冲突、namespace/open、循环和可见性

### 同名冲突

原文件只声明六个消费者/传递定理，没有 `not_prime_4884` 至 `not_prime_4888`。新增五个全名与原六个全名的交集为空，已做静态核对。

A 与 B 的证书完整常量名不同，因此在不同且正确的模块 ID 下，不会仅因叶名相同而必然发生“重复声明”。但二者都把源文件叫作根 `NonprimeCertificates.lean`，这不等于可以从相同 `import NonprimeCertificates` 自动得到两套名字。混用 A 文件和 B 限定调用（或反过来），在没有另外导入/别名的环境中会缺少所需常量。

本轮文件与 A 文件定义**相同五个全名**。不得同时从旧根模块和新相邻模块加载两份独立定义。不要将旧 A 文件、新文件、备选乘积实现或带重复 theorem 的审计源码一起导入生产消费者。未提供整个依赖闭包，不能断言这些名字在全部外部模块中没有冲突。

### namespace 与 open

共享 namespace 不等于共享模块或发生模块引用。证书通过自己的 `namespace B699CompositeTransfer20261003` 定义名字，不需要导入消费者。原消费者内也没有 `open` 语句；本轮不增加任何 `open`。原局部调用在有证据的现行 namespace 下保留，新参数使用绝对全名。

两个候选空间同时被 open 时的短名选择会受当前 namespace 等因素影响；本报告不把它一概说成必然歧义，也不依赖这种选择。当前补丁直接避免新增短名解析问题。

### 模块循环

已知新增方向是：消费者 → 新证书模块 → `Mathlib.Data.Nat.Prime.Basic`。新证书不导入消费者、不导入 4884 供应器，也不导入任何 A/B 审计文件，因此可见新增边没有回到消费者的边。同一 namespace 本身不产生 import。

原供应器及 Mathlib 的完整传递闭包没有打包；本轮只确认可见的新依赖组织，不签发全项目“无循环”结论。

### 可见性与构建

原件和新文件是普通 theorem 声明，没有 `private`、`protected`、`local` 修饰，也没有新式 `module` 头；本轮不引入可见性包装。静态源码层没有发现需要额外 `open` 或 public 导出改写的迹象；跨模块实际可见性仍由固定 Lean 的未来审计确认。

源码文件在磁盘上不等于 `.olean` 已存在，namespace 也不等于模块路径。原 receipt 使用专门的 object root 和 `effectiveLeanPath`；独立叶子和消费者输出需要与**完整模块 ID**相符且在真正使用的搜索路径中。原项目 `lakefile.lean`/`lakefile.toml` 和完整 object/搜索配置未提供，不能保证默认 Lake 构建会自动收集这个深层模块。
