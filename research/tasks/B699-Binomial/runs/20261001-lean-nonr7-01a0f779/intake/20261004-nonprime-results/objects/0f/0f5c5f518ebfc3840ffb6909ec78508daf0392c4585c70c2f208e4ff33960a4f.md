本轮只读 GitHub API 将 `v4.33.1` 解析为 Lean commit `819816b2e0a3bf405af45ae5c7af2491d8f5bee6`，随后按这个 commit 读取核心签名、内核与 elaborator 源码。

```lean
theorem succ_succ_ne_one (a : Nat) : succ (succ a) ≠ 1 := nofun
```

参数 a 显式，定理不是 private/protected，不带额外前提。`nofun` 是库自身的证明源代码，不是新文件执行 tactic。主文件用 k−2 的具体数值实例化，不在项内计算 k−2。

mathlib 固定 commit `Mathlib/Data/Nat/Prime/Basic.lean:28–29`：

```lean
theorem not_prime_mul {a b : ℕ} (a1 : a ≠ 1) (b1 : b ≠ 1) : ¬Prime (a * b) := by
```

两个隐式数参数名确为 a、b；两个显式证明参数依次对应 a≠1、b≠1。命名空间是 Nat，库内 Prime 因而是 Nat.Prime。不存在 a、b 素性或 ≥2 的隐含证明参数。库声明的 simp 已在库构建阶段产生证明，新应用不重跑该 tactic。

## 3. elaboration / 递归隐患审查

### 已排除的结构性风险（源码层）

- 两个因子均由 `(a := ...) (b := ...)` 给定，没有把 `?a * ?b = n` 留给 elaborator 求解。
- 所有数字的类型由 Nat 专用接口固定，不涉及多态环或意外整数类型；Nat.succ 的两个外层构造直接围绕数值参数。
- 新项不请求 `Decidable (Nat.Prime n)`，不沿素性判定过程搜索到 n。旧失败日志仅能证明原八处 `by decide` 报递归深度错误，未定位其内部热点，本轮也不补写虚构热点。
- 新项应用已有库 theorem；类型匹配不需要重新执行库定义里的 simp。
- `src/Lean/Meta/WHNF.lean` 固定源码中的 `withNatValue` 拒绝未解 metavariable / free variable，而本例是闭合数值；`reduceNat?` 为 Nat.succ / Nat.mul 设数值分支，`whnfImp` 在普通定义展开前尝试它。
- `src/kernel/type_checker.cpp` 中 `reduce_nat` 同样为 successor / multiplication 提供字面值分支，`whnf` 会调用它。因此不能把 `2 * 2442` 的类型核查误描述成必须递归展开 2442 层乘法定义。
- 上述内建 Nat 数值转换不是通过 `native_decide` 生成证书，也没有在本文件使用 Lean.reduceBool / Lean.reduceNat 信任入口。

### 仍不能作出的保证

没有 Lean 运行轨迹，不能给出精确最大递归深度、heartbeats、峰值内存、Expr/olean 大小、加速倍数，也不能保证任意低资源设置或任何加载状态都成功。elaborator 仍须做名称解析、Nat 实例解析、类型转换；导入 `.olean`、插件/扩展、缓存与版本错配仍可导致失败。库声明依赖闭包尚未在此运行中重放。`#print axioms` 会遍历依赖，但源码含无 tactic 并不自动证明依赖公理列表为空。

## 4. import 与命名空间

主文件唯一 import 是 `Mathlib.Data.Nat.Prime.Basic`。冻结 Basic 文件显式 public import Defs 且在 public section 声明目标引理；冻结 Nat.Basic 也在 public section。原消费者与新文件都采用 legacy 文件头（无 `module` 行），新五个完整名字为 `B699CompositeTransfer20261003.not_prime_4884` 至 `...not_prime_4888`。

原消费者在同一 namespace 内可直接用短名；无需 open，也无需更改通用接口。两个自动隐参数选项关闭后，新文件没有任何应被补成额外假设的自由名字。运行脚本会在严格选项下编译主源码本身；仅在导入后的 TypeAudit 设置选项，不能倒推主源码编译时已使用这些选项。

真正需要防范的是路径与旧对象：单独 `lean NonprimeCertificates.lean` 的源码检查不能被假定已生成可导入的对象；应明确 `-o`，在新建外部目录编译，并将该目录置于 LEAN_PATH 第一位。不要同时导入同名 R1/R2/R3 文件；更新一个规范模块即可。TypeAudit 必须导入本次生成对象，而不是把源码复制进审计文件冒充模块测试。

## 5. 不选另外两种版本的原因

`not_prime_of_mul_eq` 源码为 `h ▸ not_prime_mul h₁ h₂`。这里 h 只能是闭合算术自反项，仍需要同样的乘法定义转换；增加等式参数/运输入口，不解决新的问题。

`not_prime_of_dvd_of_lt` 需要整除证书、2≤a、a<n。整除证书本身仍要数值乘积等式，另加两个序关系证书，不比已经明确的乘积分解直接。本轮不交付替代主文件，避免误导成仍在方案摇摆。

可以确认的是主源码和顶层应用更简洁：主文件 835 字节，每条主要库应用只有两个证明参数。不能从文本长度推出最终 kernel Expr、olean 大小或实际检查耗时严格最优。
